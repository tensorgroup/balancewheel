**Goal:** At each profile checkpoint the lead writes one request file; bw runs the seats in the background,
merges and groups their findings, hands the lead `next.md`, fills every mechanical field of the `panel`
record, appends it, and gives the lead the first line of a three-line summary.

**Architecture:** A new package `panel/`: `merge.py` (parse, group, candidate disputes; pure), `record.py`
(record from findings plus verdicts; pure), `roster.py` (tier, roster, stand-ins, shortness), `state.py`
(paths, `panel.json`, `status.json`, the `panel_run` event), `channel.py` (request files in, response files
out), `render.py` and `templates/` (briefs, `next.md`), `run.py` (the detached worker: round 1 and one
`ask`), `service.py` (request handling, the one-job-per-worktree scheduler, the watchdog, `log`, `amend`),
and `cli.py` (`bw panel`). The worker runs each seat as a `bw seat` subprocess. `bw lead` calls
`service.drain` from `Session.drain`; the lead's first prompt gains `lead/protocol/panel.md`.

**Tech Stack:** Python 3.9+ standard library only (`typing.Optional`, no `X | None`); `subprocess`,
`signal`, `string.Template`, `fcntl` through `lead.paths.locked_dir`; `unittest`.

**Spec:** `docs/superpowers/specs/2026-11-22-seats-panel-guard-packs-design.md` — "End to end", "Project 2 —
`panel/`" (all of it except the `panel` config object and `seats.*.tier`, which Plan 5 Task 5 adds),
"Constraints", "Amendments to earlier documents" (the `metrics/log.py` and `metrics/store.py` bullets),
"Left to the builder" (grouping thresholds, templates, the wait helper), and "Open risks". Plan 5:

## Global Constraints

- Python 3.9+ standard library only. No YAML parser, no HTTP library.
- Tests: `python3 -m unittest discover -s tests -v` from the repo root. Tests are hermetic: they set
  `BW_STATE_DIR`, `BALANCEWHEEL_METRICS_LOG`, and `BALANCEWHEEL_CONFIG` to temp paths, and they spend no
  model quota. A live check that spends quota is a manual step in Task 14.
- Privacy firewall: fixtures in `tests/fixtures/panel/` are synthetic and hand-written. No real seat output,
  path, account, project name, or session id.
- No preview model id in an interface. Model ids are config values; tests use ids such as `"model-a"`.
- `metrics/store.py` is the only appender to the metrics log (`store.append`).
- Verdicts come from the lead's code check only. bw never grades a finding.
- Blind round 1: a seat never sees another seat's output, during or after its run. The structural guard is
  Plan 5's sandbox (the whole state dir is read-denied to a seat). bw never attaches a transcript or a seat
  file to a relay.
- Claim-only relays: an `ask` carries one claim of at most 1,500 characters inside a fixed frame.
- bw fills every mechanical field of the record. The lead sends only `verdicts`, `groups`, `severity`,
  `added`, `disputes`, and `notes`.
- Any change to a `bw` command, a module, or the log schema adds a CHANGELOG `[Unreleased]` line and runs
  `python3 docs/usage-map/generate.py` in the same commit. `bin/bw`'s docstring is its help text.
- Commit summaries are lowercase with a `feat:` / `fix:` / `test:` / `docs:` prefix. Do not commit
  `.claude/` files.
- **No change to `lead/sandbox.py`, `lead/runtimes.py`, or `lead/codepaths.py`.** A change there resets
  every lead's containment key after Plan 5 already did (Design decision 1).
- The runner has no thread alive when it forks a lead (`lead/runner.py:232-234`). The panel worker is a
  process started with `start_new_session=True`, never a thread of `bw lead`.
- The lead protocol text is a prompt for several vendors' agents: short sentences, one instruction each,
  literal paths, no shell variables.
- **Seats are not assumed verified.** `bw start` no longer verifies seats before the lead opens (Plan 5
  Task 14). Round 1 waits, bounded by `cap_s`, for a seat whose first verification on its current key is
  still running (Design decision 18). A seat that `bw seat` still refuses as `unverified` is absent
  `unverified`, and the panel calls `verify.spawn_verify(config, state, [seat])`, which never waits.
  Plan 6 never touches the attack token,
  `--attack`, or `seats.run.exec_sandboxed` (attack-only).
- Plan 6 never calls `seats.run.run_seat` with an injected `run=`. Its tests fake the whole `bw seat`
  command (`tests/fixtures/panel/fake_seat.py`), so Plan 5's `run(argv, timeout, cwd=, env=, stdin=<open
  file>, out_dir=<scratch>)` fake contract does not apply here.
- Values from the spec: at most **3** open panels per worktree; at most **20** `ask` requests per panel per
  session; claim at most **1,500** characters; `panel.max_rounds` (2) rounds per dispute; grouping at
  **±5 lines** in the same file or title-word Jaccard **≥ 0.5**; a candidate dispute at a severity gap of
  **two or more** levels; `bw-panel-wait` returns in at most 10 minutes (it uses 110 s, Design decision 8).

## Design decisions (binding)

1. **Results live in the inbox view, not a new `panel-view/`.** The spec names
   `state_dir/panel-view/<worktree key>/`. `lead_grants` already read-denies `inbox-view/` and re-reads the
   lead's own key (`lead/sandbox.py:101-104`, `:132-136`). A new parent dir would change `lead/sandbox.py`,
   its hash, and so every lead's key, a second time after Plan 5. So the view is
   `state_dir/inbox-view/<worktree key>/panels/` (`$BW_PANEL_VIEW`), with one dir per panel id, a
   `responses/` dir, and the wait helper. No write grant covers it. Seats cannot read it (Plan 5 Task 4
   read-denies the whole state dir).
2. **The worker runs each seat as a `bw seat` subprocess.** Plan 5 offers `seats.run.run_seat` in-process,
   but its interrupt cleanup works only in the main thread. A `bw seat` process handles SIGTERM itself
   (Plan 5 Task 12: exit 143, reason `interrupted`), so the watchdog can stop a whole panel with one
   `killpg`. The worker uses the
   P2-contract flags exactly: `--no-fallback`, `--brief-file`, `--session`, `-d`, `--deep`, `--out`,
   `--result`. The test override `BW_PANEL_SEAT_CMD` (a JSON list, the argv prefix) replaces
   `[sys.executable, <ROOT>/bin/bw, "seat"]`.
3. **One job per worktree at a time, reserved atomically by every entry point** (P6-3, moderator's call,
   plan panel). A job is a round 1 or one `ask`. Jobs run in request order. Plan 5's per-seat,
   per-directory lock is non-blocking (`busy`), so no two jobs of one worktree may overlap. Every entry
   point — the scheduler, a foreground `bw panel`, `bw panel --background` — takes the job through one call,
   `state.reserve_job`, under the worktree's panel lock. It fails when any panel of the worktree already
   has a `job`. The scheduler reserves **before** it spawns (pid `None`), then fills the pid, so a fast
   worker can never finish before its `job` exists (P6-25, flash 14). A foreground run reserves with its
   own pid, a deadline, and a beat, and treats SIGINT and SIGHUP like SIGTERM. Every job clears `job` on its
   way out, in a `finally`.
4. **`log` and `amend` run in the drain; `panel` and `ask` run in the worker.** `log` and `amend` are local
   and take milliseconds. A seat run takes minutes.
5. **The watchdog deadline counts every possible run** (P6-7, moderator's call, plan panel). The spec's
   `deep_cap_min + 5` minutes would kill an honest panel whose roster is larger than `max_parallel`.
   `open_panel` stores `originals` (the roster seats that can run) and `fallbacks` (the distinct enabled
   fallbacks of those seats that are not on the roster). Round 1: `(ceil(originals / max_parallel) +
   ceil(fallbacks / max_parallel) + 1) * cap_s + 300` seconds, where `cap_s` is the tier's cap and the `+ 1`
   is the first-verification wait (Design decision 18). Ask: `cap_s + 300`. Every worker, round 1 and ask,
   writes a heartbeat every 15 s.
5a. **The watchdog never trusts a stored pid alone, and stops whole trees** (P6-6, moderator's call, plan
   panel). For a job whose worker bw did not start, the stale-beat test (`beat` older than 120 s) runs
   first. Each `bw seat` runs in its own session; the worker records each one's pgid in `job.seat_pgids`.
   Every stop path — deadline, dead worker, stale beat — sends SIGTERM to the worker's group and to every
   recorded seat group (a `bw seat` kills its own CLI group on SIGTERM), sets `job.kill_at`, and waits.
   A later `schedule` call past `KILL_GRACE_S` sends SIGKILL to any group still alive, and only then calls
   `fail`, so one writer writes `findings.json`. `fail` does nothing to a panel already `ready` or `failed`.
   (Build ruling, 2026-11-23, as-built: SIGTERM to `bw seat` is the path that stops a vendor CLI. The
   SIGKILL fallback to the `bw seat` group can leave one CLI group running until its own cap. Keep
   `KILL_GRACE_S` at 15 s or more.)
6. **A candidate dispute needs a gap of two levels.** The spec's rule says "two or more levels"; its
   `findings.json` example lists a major-vs-minor pair (one level). The rule wins. The lead adds others.
7. **Literal paths in the protocol.** `lead/protocol/panel.md` is rendered per session with the real request
   and view dirs. A file-write tool does not expand `$BW_PANEL`, so one literal form serves both the write
   and the `mv`. Plan 8's G-h expansion of `$BW_PANEL` also makes a shell write with the variable an
   allow, but the protocol keeps one form. `$BW_PANEL_VIEW` is not one of the four expanded names, so it
   must never appear in a shell command. bw exports `BW_PANEL` and `BW_PANEL_VIEW`. The protocol tells the
   lead never to set, export, or unset a `BW_` variable (Plan 8 makes that a rule ask). Paths in shell
   commands are rendered shell-quoted (`shlex.quote`), apart from the plain paths given to the file tool, so
   a state dir with a space still works (P6-13, moderator's call, plan panel).
8. **The wait helper is copied into the view and takes no argument.** A contained lead may not read the
   bw checkout. bw copies `bin/bw-panel-wait` to `<view root>/bw-panel-wait`
   (`state_dir/inbox-view/<key>/panels/bw-panel-wait`, mode 0444) at session start, so no sandbox change is
   needed. Plan 8 allows exactly `python3 <that path>` with no other words, so the helper waits for **all**
   open panels of the worktree, not one id. It returns after at most 110 s (Claude Code's default tool
   timeout is 120 s); the protocol tells the lead that exit 3 means "still working, run it again"
   (P6-24). A panel with a queued or running ask counts as running (P6-4). Reading `status.json` with the
   read tool is the other path. bw computes the helper's realpath once per session and uses that one string
   in the prompt and in Plan 8's `rule_context(..., panel_wait=...)` (P6-8).
9. **The log response carries the summary's first line.** bw computes "Design panel, short (…): N findings,
   …" from the record, so the lead writes only lines two and three.
10. **Ids.** A panel id is `"p" + secrets.token_hex(4)[:7]` (8 characters, unique per worktree). The logged
    record keeps it as its `id`. Finding ids are `f1`, `f2`, … in roster order, then block order; added
    findings are `a1`, `a2`, …; group ids are `g1`, `g2`, ….
11. **`bw lead` prints nothing about panels while a lead runs.** The user works only with the lead. A
    problem (a bad request dir, a dead worker) goes to the inbox as a notice of the new kind `panel`.
    `inbox.notice` keeps one open notice per kind, which would drop a second panel problem, so it gains a
    `key` argument and dedupes on `(kind, key)`; panel notices use the panel id (or the request id) as the
    key (P6-17, moderator's call, plan panel).
12. **`findings_after_triage` is recorded only when `triage_required` is true.** It is the count of findings
    whose verdict is not `dropped`. `findings_raw` is always recorded.
13. **A failed panel logs the same way.** On failure bw writes `findings.json` from the seats that finished;
    each other seat is absent with `panel failed: <why>`. The lead logs it with a `log` request. A failed,
    unlogged panel is in `open_lines`, the wait helper's output, and the handoff, with its reason; the
    summary line says `failed` (P6-12, P6-17).
14. **`amend` merges over the whole judged request** (P6-16, moderator's call, plan panel). `log` stores the
    whole judged request (`verdicts`, `groups`, `severity`, `added`, `disputes`, `notes`) as
    `panel["judged"]`. An `amend` patch holds `verdicts`, `groups`, `severity`, `added`, and `notes`; bw
    merges it over `judged`, stores the result back as `judged` (so a second amend keeps the first), rebuilds
    `findings_detail`, and amends through `metrics/log.py`. `disputes` cannot be amended (not in
    `store.PANEL_AMENDABLE`).
15. **Unknown keys in a `log` or `amend` request are ignored and named** in the response's `ignored` list.
    The envelope keys `v`, `type`, `panel`, and `nonce` are stripped first and never listed. A request
    whose fields have the wrong type (`"groups": null`, `"added": "x"`, `"disputes": [{}]`) gets an
    `{"ok": false}` response: `record.build` raises `ValueError` for every shape fault, and `drain` also
    maps `TypeError`, `KeyError`, and `AttributeError` to `"malformed request: <type>"` (P6-16, neon 8).
16. **Panel ids in requests are checked twice** (P6-1, moderator's call, plan panel). `channel.parse`
    refuses a `panel` field that fails `PANEL_ID = ^p[0-9a-f]{7}$`, and every service entry point refuses a
    loaded panel whose `project` is not the request's worktree key ("unknown panel"). No path is built from
    an unchecked id.
17. **Responses echo the request, and a reused request id is refused under a new name** (P6-15, moderator's
    call, plan panel). Every request may carry `"nonce"` (at most 32 characters); every response holds
    `"nonce"` (the request's, or `null`) and `"received"` (bw's epoch seconds). A stem whose response file
    already exists gets the refusal `{"ok": false, "error": "request id <id> was used before; send the
    request again with a new id", "nonce": ...}` in `responses/<id>.reused-<n>.json`, and one `panel`
    notice. The old response is left as it was. The protocol tells the lead to check that the response's
    nonce is its own.
18. **A seat whose first verification is still running is waited for** (P6-19, the moderator's own
    finding). Before launch, round 1 asks `roster.pending_verify` which roster seats are unverified only
    because no verification has finished on their current key (`seats.json` `failed_probe` is `"never
    verified"` or `"key changed"`). For those, it calls `spawn_verify` (a `False` return means one is already
    running) and polls every 5 s until each such seat is verified, or no verify is running
    (`state_dir/seats/verify.lock` is free), or `cap_s` passes. Then it launches. A seat with a recorded
    failure on its current key is not waited for. After round 1, the same rule picks which unverified seats
    get a `spawn_verify` call (Task 8 step 5a) (build ruling, 2026-11-23, as-built). So a new install does not give an all-absent first panel.
19. **Lead-written text is escaped and bounded like seat text** (P6-20, moderator's call, plan panel).
    `record.build` passes every lead string through `safe()` and cuts it: `title` `TITLE_CHARS`, `where`
    `WHERE_CHARS`, `claim` `CLAIM_CHARS`, dispute `summary` and `reason` 500, each `proposals` value 1,500,
    `notes` 2,000.
20. **Reserved seats run on deep panels only, by any route** (P6-9, moderator's call, plan panel). On the
    standard tier, a reserved seat listed in the checkpoint is absent `reserved: deep panels only`, and a
    reserved fallback never stands in. On the deep tier, disabled reserved seats are not added. A stand-in
    never gets a stand-in (one hop, also on a mid-run cap), and a fallback that is already absent is never
    marked as standing in.

## Review Focus

- **A hostile or broken request file** (bad JSON, 10 MB, a symlink, a FIFO, a dir named `x.request`, an id
  with `/` or `..`, a `panel` field of `../other/p1234567` or a valid id of another worktree) — the drain
  never hangs or raises; a valid id gets an `{"ok": false}` response; one `panel` notice names the problem,
  escaped and cut; no other worktree's panel is read or changed; other requests still go through. Test in
  Task 6 and Task 9.
- **`bw lead` exits, or the lead switches, while a panel runs** — the worker keeps running and holds no
  descriptor of the worktree lock; the next session reaps it or marks it failed by its heartbeat; the
  handoff lists the open panel. Test in Task 9 and Task 11.
- **A seat prints a hostile block** (control characters, 10,000 entries, numbers where strings belong, a
  fence inside a claim, two JSON blocks) — at most 50 findings per seat, every string escaped and cut, bad
  entries skipped, the last valid block wins, no block gives one "unparsed output" finding. Test in Task 2.
- **The lead logs twice, logs too early, logs an unknown panel, or amends before logging** — each is
  refused with one clear error; the second `log` says "already logged; send an amend". Test in Task 9.
- **Every seat is absent** (all capped, or every verification failed) — the panel is `ready` and short
  with zero findings; it logs with empty `seats`; the summary line says so; watches and the dashboard read
  it without error. On a new install, where the first verifications are still running, round 1 waits for
  them (bounded by `cap_s`) instead (Design decision 18). Test in Task 1, Task 3, and Task 8.

  severity `minor`, where `""`, claim `"bw found no JSON block; read seats/<seat>.md"`.
- Produces: `group(findings: list) -> list` — `[{"group": "g1", "title": <first member's title>, "members":
  [finding, …]}]`. Two findings join when both have a file and line (`where` split at its last `:` into a
  path and an integer) in the same file within `LINE_WINDOW` lines, or when the Jaccard index of their title
  words is at least `JACCARD`. Title words: lowercase `[a-z0-9]+` tokens of 3 or more characters. When

  2026-11-23). Joining is transitive (union-find). Group ids follow the first member's finding order.
- Produces: `candidate_disputes(groups) -> list` — `[{"id": "d1", "group": "g1", "reason": "severity critical

**Interfaces:**
- Consumes: Task 2's `findings.json` document; `log.compute_counts`, `log.validate_panel`, `log.SEVERITIES`,

- Produces: `REQUEST_KEYS = ("verdicts", "groups", "severity", "added", "disputes", "notes")`,
  `GROUP_ID = re.compile(r"[A-Za-z0-9_-]{1,32}")`.
- Produces: `build(doc: dict, req: dict, config: dict, moderator: Optional[dict] = None, rounds: int = 1)
  -> (dict, list)` — returns `(record, ignored keys)`. Raises `ValueError` with one message:
  - `"missing verdicts: f2, f5"` when a numbered finding has no verdict; `"unknown finding ids: f9"` for a
    verdict, group, or severity on an id that does not exist; a verdict not in `VERDICTS`; a severity not in
    `SEVERITIES`; a group id that fails `GROUP_ID`.
  - `added` entries need `seat` (a seat whose status is `ok`), `title`, `severity`, `verdict`, and may have
    `where` and `group`; each gets id `a1…` and, without `group`, a new group `ga1…`.
  - `disputes` entries: `challenger` and `winner` are seats whose status is `ok`; every `proposals` key is
    such a seat. The shape check itself stays `validate_panel`'s.
  - **Shape faults are `ValueError`** (Design decision 15): `verdicts`, `groups`, `severity` must be
    objects of string → string; `added` and `disputes` lists of objects; a missing key in an entry names
    the entry (`"added[0] missing title"`, `"disputes[0] missing winner"`). No `TypeError`, `KeyError`, or
    `AttributeError` leaves `build`.
  - **Lead text is escaped and cut** (Design decision 19): every lead string goes through `safe()`, then
    `title` ≤ `merge.TITLE_CHARS`, `where` ≤ `merge.WHERE_CHARS`, `claim` ≤ `merge.CLAIM_CHARS`, dispute
    `summary` and `reason` ≤ 500, each `proposals` value ≤ 1,500, `notes` ≤ 2,000. `target` comes from bw
    and is escaped the same way.
  - The record: `target`, `kind` (the checkpoint), `tier`, `seats` (seat → model, `ok` seats only),
    `absent`, `rounds`, `immediate_agreement` (`not disputes and rounds == 1`), `findings_raw`,
    `findings_after_triage` (only when `doc["triage_required"]`: findings whose verdict is not `dropped`),
    `findings_detail` (`{"id", "seat", "group", "title", "severity", "verdict", "where"}` per finding, with
    the lead's `groups` and `severity` applied), `findings` (`log.compute_counts`), `disputes`, `notes`,
    and `moderator` when given. Every other key of `req` is in the ignored list.
- Produces: `summary_line(rec: dict, doc: dict) -> str` — exact copy, from the spec's example:
  `"{Tier}{Checkpoint} panel{, failed: <why> | , short} ({seats}{; absent}): {n} findings, {c} confirmed, {r} refuted, {d} dropped."`
  where `Tier` is `"Deep "` on the deep tier, else empty; `Checkpoint` is the checkpoint capitalised;
  `, failed: <why>` replaces `, short` when `doc["failed"]` is set, so the user sees a failed panel in the
  lead's summary (P6-17);
  `seats` is the `ok` seats in roster order, a stand-in written `gem for astra` only when it was not on the
  roster; `absent` is `astra absent: usage cap` items joined by `, `; `n` counts every finding including
  dropped; `, {p} partial` is inserted after `confirmed` only when `p > 0`. With no `ok` seat the
  parenthesis is `(no seat returned; astra absent: usage cap, …)`.
- Produces: `judged(req: dict) -> dict` — the request's `REQUEST_KEYS` only, as stored in
  `panel["judged"]` (Design decision 14).
- Produces: `merge_patch(old: dict, patch: dict) -> dict` — `old` is a whole `judged` dict; `verdicts`,
  `groups`, `severity` merge by key; `added` and `notes` replace when present; `disputes` is kept from
  `old`; other keys are ignored (the caller reports them). The result is the new `judged`.

  `seat_grants` signature.
